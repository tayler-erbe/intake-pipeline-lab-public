TAYLER ERBE / SYSTEM DESIGN · DOCUMENT INTAKE

One stage at a time. One model at a time. Nothing overwritten.

My model evaluation found no single model that reads every part of a document well. Tables, page text, charts and clauses each need a different route. This is the pipeline that runs those routes on hardware with one GPU, and keeps every answer traceable to the page it came from.

Short version: each stage is one line of configuration. Swap the model, and the pipeline records a new version instead of replacing the old one. Code copies the text; models only point to it.

THE DESIGN IN THREE IDEAS

Change one line.
Keep the old answers.

// stage "fields"
- "served_model": "qwen3:32b"
+ "served_model": "gpt-oss:20b"

Every job is identified by its stage, model, version, prompt and input. A new model means new jobs, so earlier results stay as their own version and can be compared side by side.

Read everything. Unload.

Stages run in order across every document, so each model loads once per batch instead of once per document. A stop or crash loses at most one job.

00 / WHY IT MATTERS

Piles of documents,
one small GPU.

Contracts, leases and subscriptions hold the dates and dollars an organization has to act on. Finding them by hand is slow, and AI that reads a page wrong can be worse than no AI at all.

THE DOCUMENTS

Every file is a mix

One contract can hold typed pages, scans, price tables, charts and highlighted clauses. No single AI model reads all of them well.

THE HARDWARE

Private and local

Sensitive documents should stay on the organization's own machine. That usually means one graphics card, which can hold one large model at a time.

THE TRUST

Show your work

A date or dollar amount is only useful if a person can see exactly where it came from and decide whether it is right.

01 / THE LINE

An assembly line,
not a chatbot.

Documents are split into segments: prose, tables, forms, charts and highlighted passages. Each stage takes only the segments it handles, in order, across the whole batch.

  1. 01 / TAKE IN

    Ingest and triage

    Hash every file, skip duplicates, quarantine what can't be opened safely. Find native text, scanned pages, tables, forms, charts and highlights, and flag skewed or rotated pages.

  2. 02 / READ

    Text first, models second

    Copy native text straight from the file. Reuse earlier OCR when it exists. Send only scanned pages to a page-reading model.

  3. 03 / LOOK

    A route per region

    Layout, figure type, tables, charts and highlights each go to the model that tested best for that task.

  4. 04 / UNDERSTAND

    Fields, then checks

    A text model points to the evidence for each field. Code normalizes dates, money and terms, then suggests document type and metadata.

Configure it.
Swap it.

Every stage is one entry in a routes file: which backend, which served model, which prompt, and the limits it runs under. Changing a model is a configuration change, not a code change.

// one stage in routes.json (shortened)
{
  "stage": "chart",
  "unit": "segment",
  "backend": "local_model",
  "provider": "ollama",
  "served_model": "qwen3-vl:8b",
  "select": { "kind": ["chart"], "source": ["raster"] },
  "prompt": "Extract the data shown in this chart as a table...",
  "schema": "evaluated_table_schema",
  "max_output_tokens": 3000,
  "max_side": 1600,
  "read_policy": "single",
  "evaluated_configuration": {
    "reproduced": ["prompt", "schema", "token budget", "image cap"],
    "not_reproduced": ["weights", "server"]
  }
}

What each part does

select decides which segments reach the stage. provider and served_model name a local server and model: Ollama or any OpenAI-compatible server such as vLLM. prompt, schema and the limits are sent exactly as written.

evaluated_configuration says which settings match how the route was tested and which do not. A check-out report prints it, so nobody mistakes a changed route for the tested one.

Alternative routes sit beside the defaults, unused. To try one, replace the stage entry with it. The default text model, for example, has a smaller candidate waiting.

Models run locally. Document content never goes to a hosted AI service.

02 / SWAPPING A MODEL

Six steps,
no rebuild.

The same steps work for any stage, and for any model a local server can host.

  1. Edit the route

    Change the served model, and the prompt or limits if the new model needs them.

  2. Run the check-out

    Each stage reads a small fictional test set. A stage passes only if its model is served and its output parses.

  3. Refuse, don't substitute

    If the model isn't installed or served, the stage refuses. It never falls back to another model quietly.

  4. Run the stage

    New jobs get a new identity. Earlier results stay in place as their own version.

  5. Compare versions

    Both versions sit side by side for the same segments, so the change can be measured, not assumed.

  6. Choose current

    A pointer records which version is current for each document, and the others stay on file.

03 / RULES

What keeps the
output honest.

Each rule is enforced in code and covered by automated tests, not left to a prompt.

EVIDENCE

Models point, code copies

The text model returns evidence IDs, not text. Code copies the quoted words from the page, so a value can't contain words the document doesn't.

Every value has a page and position

Proves where text came from, not that it answers the question. Accuracy still needs review.

PRODUCERS

Every value says who made it

Each value is labelled code, rules, model or stub. Test-stub output is never searchable, exported or offered for review as fact, and anything derived from it inherits the label.

Placeholders can't leak into results

STATES

Absent only after a full read

A field is absent only when every page was read. Otherwise it is unread, failed, rejected or insufficient, and says which.

No false "not found"

VERSIONS

Nothing is overwritten

A job's identity is its stage, backend, model, version, prompt hash and input hash. Changing any of them creates new jobs alongside the old ones.

Every run can be compared

ONE GPU

One model resident

Before each load, the pipeline checks what is already on the GPU, for every server kind, and refuses if another model is still there.

Built for one 24 to 48 GB card

RESTARTS

Stop anywhere, resume safely

Work is committed per job. Pause, resume, retry limits, a runtime lock and a quarantine are part of the design, not afterthoughts.

A crash loses at most one job
!

Traceable is not the same as correct.

A value copied from the right page can still answer the wrong question. That is why every model-proposed value goes to a person before it counts, and why accuracy is measured separately.

How it will be measured ↓

Swap the domain,
not the code.

What to extract lives in a field catalog: each field's name, category, type, whether it is critical, and how to normalize it. A different kind of document gets a different catalog.

CATALOG 1

Procurement

Contracts, leases, service subscriptions and consulting scopes. Fields grouped into ten categories: dates and terms, termination, pricing and payment, scope, products, leasing, rights, parties, identifiers, and risk.

CATALOG 2

Proposals and awards

A second, provisional catalog with its own fields and vocabulary, to show the same line serving a different domain.

SAFETY

No mixing

Each runtime records its catalog and refuses to open under a different one, so two domains' fields never mix in one database.

CHANGE

Proposed, then approved

New fields load as proposals until the owner approves them. The catalog is versioned like everything else.

04 / REVIEW AND OPERATIONS

Built for the person
checking the work.

Extraction is half the job. The rest is letting a reviewer find, check and correct values quickly, and letting an operator run it unattended.

REVIEW

Workbench and queue

One offline page per batch: each document's fields beside cropped source regions. A queue puts the riskiest values first. Decisions are exported and imported as files, with duplicate imports refused.

SEARCH

Plain-language questions

Questions like "leases over $100,000 that auto-renew" become filters. Rules parse the question; an optional small local model can help, but rules win and code converts every number and date.

LINKS

Related documents

Amendments, references, shared identifiers, near-duplicates, and a scan matched to its clean original. All are proposals for a person to confirm.

DATES

Obligations calendar

Renewal, notice and expiry dates from reviewed values, exported as a calendar and spreadsheet.

OPERATIONS

Inbox and status page

Drop files in a folder; a poller waits for them to settle, runs the line and writes a status page. Pause, stop, retry and purge leave an audit trail.

FORMATS

PDF, Word and Excel

Office files are parsed as data, not printed to images. Spreadsheets keep their cells and numbers.

Where it stands.

The pipeline is built and tested end to end on fictional documents, with placeholder models standing in for real ones. No accuracy is claimed. That comes from a labelled pilot, measured the way the model evaluation was.

01 / CHECK OUT

Real models in place

Install each route's model on the target machine and pass the check-out, stage by stage.

02 / RUN

Real documents

Run the full line with real models on a sample set, locally, and fix what real documents expose.

03 / MEASURE

Labelled pilot

Reviewers label 100 to 300 documents. Accuracy is reported per field against a locked holdout, with confidence intervals.

04 / CALIBRATE

Tune on evidence

Set thresholds and swap routes only where the pilot shows a measured gain.

Why a pilot, not a benchmark. Public benchmarks chose the starting models. Only labelled documents from the real domain can say how well the whole line works, field by field.
